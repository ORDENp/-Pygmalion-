# С.В.Г. — Связь метронома v0.4.04 с идеей «собственной временной геометрии секторов»

**Статус:** АНАЛИЗ (задание директора по ПП). Код сегодня НЕ меняется.
**Дата:** 2026-09-26. **Автор:** ZCode.
**Это не решение** — только карта технической возможности, выводы и риски.

---

## 0. Что я понял под С.В.Г. (гипотеза — требует подтверждения директора)

Сектор — географическая область, определяемая по GNSS (GPS/ГЛОНАСС).
«Собственная временная геометрия сектора» — предположение, что фазовый поток
(IMPULSE/ACTIVE/SILENCE) может привязываться к сектору, а не быть единым
для всей планеты. **Что именно меняет сектор — фазовые границы или только
данные о месте — в задании не зафиксировано. Это первый вопрос, без которого
анализ дальше невозможен.**

---

## 1. Метроном остаётся единственным источником фазы и burn_at

Технически привязка возможна **только через метроном** — все фазовые решения
v0.4.04 уже сведены к одной точке:

```text
Metronome.getCurrentTime()      ← единственный вход времени
        ↓
getCurrentPhase() / getDayKey() / isNewDay() / calculateBurnAt()
        ↓
planPass / tokPass / umTransfer / tick / cron-wake
```

Единственный безопасный способ ввести сектор: **один параметр-контекст**,
передаваемый В метроном, а не рядом с ним:

```text
Metronome.getCurrentPhase(context)   context = { sector: '...' }
```

Тогда любой компонент (space-session, cron, frontend) по-прежнему спрашивает
фазу только у метронома; сектор не становится вторым источником времени.
Если же секторный сдвиг вычислять вне метронома — мы вернёмся к ситуации
«cron считает ACTIVE, метроном считает SILENCE», которую только что устранили.

## 2. Точки интеграции (карта, без изменений кода)

| Точка | Роль сегодня | Возможное вхождение сектора | Затронутый канон |
|---|---|---|---|
| `metronome.getCurrentTime()` | единственный вход времени | не трогать: GNSS-время не нужно — метроном уже точнее | — |
| `metronome.getCurrentPhase(ctx)` | фаза | опциональный контекст `{sector}` — параметр №1 | единое ::0:: (см. риск R1) |
| `metronome.calculateBurnAt(ctx)` | burn_at | тот же контекст — burn_at сектора | replay-детерминизм (R6) |
| `metronome.getDayKey/isNewDay` | день для cron | день становится секторным → cron wake спрашивает по каждому активному сектору | cron-архитектура |
| `space-session` (planPass/tokPass/umTransfer) | допустимость действий | читает фазу только через метроном — изменений нет, контекст проходит сквозь | — |
| `acts_log` | каноническая запись | сектор как атрибут акта — **нельзя задним числом**: Decision 02 Crystal Bridge (acts_log неизменяем) | Decision 02 |
| frontend | отображение | показывает фазу и сектор, ничего не решает | принцип «браузер не решает фазу» |

Ключевое: **сектор входит одним параметром в метроном**, дальше система не
меняется структурно. Все пять точек входа действий (planPass/tokPass/umTransfer/
tick/cron) уже спрашивают метроном — им сектор не нужен отдельно.

## 3. GNSS: что он даёт и что не даёт

GPS/ГЛОНАСС даёт две вещи: **координаты** и **точное время**.

- Время от GNSS системе Пигмалиона НЕ нужно — метроном уже является
  авторитетным временем (и независим от внешних сигналов). Принимать
  GNSS-время означало бы второй источник времени — прямо противоположно
  только что выполненному заданию.
- От GNSS нужен только **сектор по координатам** (калибровка).

Предложенная директором логика доступа (как я понял):

```text
автокалибровка сектора — по GNSS, автоматически
повторная калибровка   — вручную, в любое время
ручной выбор С.В.Г.    — только после 90 дней неактивности без эмиссии У.Е.,
                         при повторном получении О.К.
```

Замечание по 90 дням: в каноне уже существует 90-дневное правило
(глоссарий v0.5: бездействие 90 дней → Вр.О.К., платформенный У.М.
возвращается Платформе). Правило сектора либо опирается на этот же
механизм, либо создаёт второй 90-дневный счётчик — дублировать нельзя,
нужно одно решение.

## 4. Выводы

1. **Техническая возможность — да.** Привязка сектора к метрону реализуема
   одним параметром-контекстом, метроном остаётся единственным источником
   фазы и burn_at, структурные изменения системы не требуются.
2. **Время от GNSS не используется** — только определение сектора по координатам.
3. **Точки входа уже готовы**: все действия спрашивают фазу у метронома,
   сектор проходит сквозь один параметр.
4. **Главное ограничение — не техническое**: концепция «собственной временной
   геометрии» в предложенном смысле (секторные фазы) противоречит проверенному
   принципу единого ::0:: (см. R1). Технический крючок лёгок; системный смысл —
   зона решения стратега.

## 5. Риски

- **R1 — распад единого ::0::.** Если фазы становятся секторными, общая
  тишина исчезает: человек в Калининграде передаёт У.Е. человеку на Камчатке,
  который в это время в SILENCE. Т.О.К. требует фазового ответа получателя.
  Это не запрет — это вопрос, на который должна ответить модель: чья фаза
  govern-ит транзакцию между секторами.
- **R2 — суверенитет человека.** Координаты — слежение. Хранить можно только
  сектор (агрегат), никогда координаты и не трек; отказ от GNSS обязан иметь
  ручной путь, не блокирующий участие.
- **R3 — достоверность.** GNSS подделывается (spoofing), человек может быть
  в VPN/в пути. Нужны правила стабилизации сектора (смена не мгновенно,
  а по устойчивости) — иначе фазовая геометрия дрожит.
- **R4 — канон.** Сектор как атрибут акта требует нового канонического решения
  (Preview → Confirmation → Execute → Replay), acts_log задним числом не меняется.
- **R5 — пересечение с Вр.О.К.** Второй 90-дневный счётчик — риск двойных правил.
- **R6 — Replay.** Replay воспроизводит фазы детерминированно; секторный
  параметр обязан попасть в лог события, иначе прошлое нельзя будет
  восстановить.
